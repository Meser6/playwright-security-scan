# Changelog

All notable changes to this project are documented in this file. The format is based on
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and this project adheres to
[Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- Attack mode with ZAP (optional): `PW_SEC_MODE=attack` runs the tests like `scan`, then starts `zaproxy/zap-stable` in Docker (or uses a ZAP you started, `attack.zapUrl` with `PW_SEC_ZAP_API_KEY`), gives it the requests of the tests (`sendRequest`, no spider), runs the active scan in the session of one role within a budget (`attack.maxRequests` 2000, `attack.maxRps` 10, `attack.maxDurationMinutes` 30) and maps the alerts to findings `zap.<pluginId>` with the same fingerprints, baseline and gate; `PW_SEC_MODE=attack-baseline` writes them to the baseline. `attack.allowedOrigins` is required (no default), production-looking origins stop the run (`attack.denyOrigins`, `attack.iUnderstandThisIsNotProduction`), only reading methods by default (`attack.methods`), every ZAP request carries `x-pw-sec-probe`, and the container is stopped after the scan, after an error and on Ctrl+C. Without Docker the run ends with `ATTACK_DOCKER_MISSING` and the passive result. On Linux the container uses `--network host`; elsewhere a local origin needs `attack.zapUrl`. `zap.*` baseline entries are resolved only by a completed attack run. New: an Attack tab and a ZAP badge in the HTML report, `attack` in `report.json`, the SARIF category `pw-sec-attack`, a `zap` JUnit suite, `rules['zap.<id>']` settings, the evidence kind `attack`, the codes `ATTACK_*` (also `ATTACK_SHARDED` for `--shard`), `docs/attack.md` and the "Nightly attack run" recipe in `docs/ci.md`. Attack templates of the worker (attachment `pw-sec-templates`, list `attack`) keep request bodies of JSON, forms and plain text with credential-like fields replaced by `[redacted]`.
- Authorization tests, off by default: with `authz: { enabled: true, allowedOrigins: [...] }` in the package config, a `scan` or `baseline` run replays the GET and HEAD requests of your tests after the last test, as the other roles of your Playwright project (projects with a `storageState`, `authz.roles` for shared roles and levels) and without a session, and reports `authz.unauthenticated-access`, `authz.horizontal` (IDOR) and `authz.vertical` when the answer is like the one of the allowed user. These are the only requests the package ever sends, from a module loaded only then: only GET/HEAD, only to `authz.allowedOrigins` (required, no default; checked again before each request, redirects are not followed), never to production-looking origins (`www.`, `prod`, a domain without a subdomain; `authz.iUnderstandThisIsNotProduction`, `authz.denyOrigins`), within a budget (`authz.maxRequests` 500, `authz.maxRps` 5, `authz.maxDurationMinutes` 10) and with the header `x-pw-sec-probe: <run id>`. Endpoints seen without a session in the run are public and not tested. The worker keeps request templates without credentials and salted digests of the answers (attachment `pw-sec-templates`), never bodies. `PW_SEC_AUTHZ=0` switches the tests off for one run; a check prints the plan without sending anything. Findings go through the baseline and the gate; an `authz.*` entry is resolved only when its role pair was replayed and denied. New: an Authorization tab in the HTML report, `authz` in `report.json` and `coverage.authzObserved`, the evidence kind `replay`, an `Authz` row in the start banner and the check, the codes `AUTHZ_*`, step 4a of the guided setup (default no) and `docs/authz.md`. Sharded runs replay per shard and the merge judges the results. `PW_SEC_MODE=active` now points to `authz.enabled`.
- 11 new passive rules, all in the `recommended` preset (now 55 rules, `strict` 57): `auth.session-fixation` (a session cookie keeps its value across the login request), `auth.session-in-url` (`;jsessionid=`, `sid`, `phpsessid`, `session_id` in the URL), `cache.sensitive-cacheable` (a response to a request with a session cookie or `Authorization` without `Cache-Control: no-store` or `private`), `browser.csrf-missing` (a state-changing request with a session cookie without `SameSite=Lax/Strict` and without a CSRF token or header; low confidence, never blocks by default), `asset.unexpected-third-party` (a script from an origin outside the new option `allowedScriptOrigins`; without the option an inventory at severity info), `data.pii-in-url` (e-mail address, PESEL or E.164 phone number in the query), `data.card-number` (a full card number with a valid check digit in a response; provider test cards and masked numbers are skipped), `cookie.broad-domain` (a session cookie with a `Domain` attribute), `disclosure.internal-hostname` (`.internal`, `.local`, `.lan`, `.corp`, `.intranet`, `svc.cluster.local` host names; low confidence on localhost), `disclosure.verbose-error-json` (`stack`, `exception`, `trace`… keys in a 4xx/5xx JSON) and `browser.password-form-get` (a password form sent with GET). Two new rule groups, `auth` and `cache` (JUnit suites, HTML filter chips). Docs in `docs/rules/`.
- Evidence of every rule now redacts e-mail addresses, PESEL numbers, E.164 phone numbers and card numbers (`[email sha256:…]`, `[card visa sha256:…]`), and the values of the session parameters of `auth.session-in-url`.
- Custom rules can read the whole browser traffic of a test at its end: `appliesTo: { testEnd: true }` gives `check` one `TestTraffic` input (`kind: 'test-end'`) with the in-scope requests in order, the cookies sent and set (a salted hash and a value class, never the value), a login flag and a CSRF signal; `playwright-security-scan/rules` exports `TestTraffic`, `TrafficRequest` and `CookieValueClass`. `defineRule()` no longer rejects `testEnd`.

- Sharded runs: a `scan` or `baseline` run with `--shard=i/n` writes `reports/pw-sec/shard-<i>-of-<n>.json` instead of judging its part of the traffic, and `PW_SEC_MODE=merge npx pw-sec` (no browsers, no tests) merges the shard files of all machines into one result: one `report.json`, HTML report, SARIF, JUnit and `outcome.json`, and in `baseline` mode one complete baseline. The merge checks the set (`MERGE_SHARD_MISSING`, `MERGE_SHARD_MISMATCH`, `MERGE_SHARD_DUPLICATE`, `MERGE_WRONG_DIRECTORY`, …) and exits with the result code. `--shard` is no longer a filter for `PARTIAL_RUN`. `report.json` has the new field `shards` and `outcome.json` the fields `mode` and `shard` (`SHARD_WRITTEN` for a shard run); `PW_SEC_MODE=merge` in the test command is `MODE_INVALID`. Recipes for GitHub Actions and GitLab CI in `docs/ci.md`, "Sharded runs".

- Custom rules (experimental): write your own passive rule with `defineRule()` from the new `playwright-security-scan/rules` entry point and list it in `rules.custom` of the package config. Ids are `custom.<name>`; findings get fingerprints, go into the baseline, block above the gate and appear in every report (a `custom` badge in the HTML report, a `custom` tag and your `docs.url` in SARIF, a `custom` suite in JUnit). Presets and `rules['custom.<name>']` settings work as for built-in rules. A rule that throws is reported as `CUSTOM_RULE_ERROR` with the rule id and the line in your file, and the result is `TOOL_ERROR` (exit code 3); a rule that returns a promise is `CUSTOM_RULE_ASYNC`. Invalid definitions are `CONFIG_INVALID_RULE` or `CONFIG_DUPLICATE_RULE`. The entry point also exports the input types (`ResponseRecord`, now with `kind: 'response'`, `BrowserEvent`) and the helpers `getHeader`, `getHeaders`, `parseSetCookie`, `decodeJwt` and `builtinRuleIds`. See `docs/custom-rules.md`.

### Removed

- Environment labels: `PW_SEC_ENV`, the `run.env` option, `security-baseline.<env>.json` files, the `env` field of the baseline file, `report.json` and `outcome.json`, the environment in the console, HTML report, SARIF category and JUnit root, and the environments step of the guided setup (now eight steps, `[1/8]` to `[8/8]`). A set `PW_SEC_ENV` only gives the warning `ENV_REMOVED`; `run.env` in the config is an unknown option (`CONFIG_UNKNOWN_OPTION`); an `env` field in an existing baseline file is ignored and dropped by the next `baseline` run. For several environments, set `baseline.path` from your own variable (`docs/faq.md`, "Several environments"). `report.json` and `outcome.json` now have `schemaVersion: 2`. The codes `ENV_INVALID`, `BASELINE_ENV_MISSING` and `BASELINE_ENV_MISMATCH` are gone.

### Changed

- HTML report: a click on a finding opens its details in a dialog like the key window of the perf report (Previous / Next finding over the visible rows, Close, `Esc` and a click outside close it and return the focus to the row, Copy link). `report.html#finding=<fingerprint>` opens the dialog of that finding right away, also in the report of another run; an unknown fingerprint says "Finding not found in this report".
- The HTML report has the look of the playwright-performance-regression report: an app bar, the verdict card, six counter tiles that open the filtered list, tabs (Findings, Coverage, Run & config), filter chips, search and sortable columns, a light and a dark theme, and a Content-Security-Policy that allows only its own script and styles. The page is rendered in Node and works without JavaScript (every tab shown, details of each finding in its row). The details show the state against the baseline, the fingerprint with Copy, the location, the evidence, the tests that saw the finding (from the test tree, the first with its step), the rule's Why, Fix, False positives and references, and the baseline entry to paste. Grouping is now done by sorting the Rule or Subject column.
- The check of the guided setup (`npx pw-sec`) is one quick trial run with `PW_SEC_MODE=check` (up to 10 tests, nothing written) instead of three runs (`check`, `baseline`, `scan` with a temporary baseline). Its result is read from the check output: "The scan sees your app's traffic." or the cause (no traffic in scope with the origins seen outside it, or the first error). The internal `PW_SEC_BASELINE_DIR` variable is gone.

### Fixed

- WebKit: redirects are analysed again (`browser.open-redirect-candidate` and the headers of 3xx responses); they were skipped as mocked because WebKit gives no server address for them.
- Firefox and WebKit: a session cookie without `SameSite` read from the cookie jar no longer gives `cookie.samesite-none`; these engines report a missing attribute as `None`. The same app now gives the same findings in every browser. The `cookie-jar` event of custom rules has the new optional field `missingSameSite`.

## [0.2.0-beta.0] - 2026-11-26

### Fixed

- A cookie whose name looks like a session (`session-username`, `auth`) but whose value is plain words (`standard_user`, `true`) is no longer taken for a session cookie (false positive of `cookie.no-httponly` and `cookie.no-secure` on SauceDemo).
- A baseline run no longer reports its new findings as warnings in the verdict: they were just written to the baseline.

### Added

- `docs/init.md` describes the guided setup; the README starts with `npm init playwright-security-scan`.
- `npx pw-sec` and the new `create-playwright-security-scan` package (`npm init playwright-security-scan`): the start of the guided setup — installation, the tutorial question, 7 languages (`PW_SEC_LANG`), `PW_SEC_DRY_RUN`, `PW_SEC_NO_TUTORIAL`, what the package does and how to run it, and checks for a missing `playwright.config` or an old Playwright. Then the questions (rule preset, gate, origins of your app with suggestions from your sources, environments, test command) and the changes, each shown as a diff before it is written: a short `pw-sec.config.*` (TypeScript, ESM or CommonJS), `withSecurity()` in `playwright.config` (outside `withPerf()`, also fixing the reverse order), `withSecurityFixtures()` in your fixtures module or the `playwright-security-scan/test` import in test files, and `reports/pw-sec/` in `.gitignore`. A second run changes nothing. At the end the wizard offers a check — your test command runs with `PW_SEC_MODE=check`, then `baseline` and `scan` with the baseline in a temporary folder — and explains a failure (no traffic in scope, a tool error, unstable traffic); it ends with an IMPORTANT box with the exact commands for your project (per environment label, `cross-env` on Windows).
- Documentation like the perf package: `docs/cli.md`, `docs/configuration.md`, `docs/baseline.md`, `docs/reports.md`, `docs/ci.md` (GitHub Actions, GitLab, Azure DevOps, Jenkins, environments, schedule), `docs/adoption.md`, `docs/faq.md` and `docs/upgrading.md`; the README is now a short introduction with links, and the rules table lives in `docs/rules/README.md`.
- `playwright-security-scan/test`: a ready `test` and `expect` for specs that import them from `@playwright/test`, so set-up needs no fixture module (one import change per spec file).
- Dry run: `PW_SEC_MODE=check` runs the first test of each file (at most `PW_SEC_MAX_TESTS`, default 10) and prints the origins in scope with their responses, the traffic outside the scope, the scanned projects, the rules, the baseline state, how many findings would be new and a `READY` / `NOT READY` verdict. Nothing is written. `report.json` coverage now lists the origins outside the scope (`outOfScopeOrigins`).
- One baseline per environment: `PW_SEC_ENV=qa` (or `run.env` in the config) uses `security-baseline.qa.json`. The label is checked before the run (`ENV_INVALID`), never falls back to the file without a label (`BASELINE_ENV_MISSING`), is written to the baseline file (`BASELINE_ENV_MISMATCH` when it differs) and appears in the console, `report.json`, `outcome.json` (`env`), the HTML report, SARIF (category `pw-sec/<env>`) and JUnit.

### Changed

- The console output looks like the one of `playwright-performance-regression`: colors in a terminal (`NO_COLOR`, `FORCE_COLOR` and `TERM=dumb` are respected), the start banner as a table, errors and warnings in framed boxes, the counters and the blocking findings in tables, the verdict in a box (`✅ PASSED`, `⚠ PASSED WITH WARNINGS`, `❌ FAILED`, `❌ ERROR`) with the result name and code, and one `Report:` line with the absolute path of the HTML report. The text is the same without colors and still fits in 30 lines.

## [0.1.0-beta.0] - 2026-11-25

First test release, published under the `next` dist-tag (`npm i -D playwright-security-scan@next`).

### Fixed

- Google Analytics, consent and CDN cookies (e.g. `_ga_*`, `cf_clearance`) are no longer taken for session cookies; the session heuristic is configurable with `nonSessionNames`.
- `data.password-in-response` no longer reports labels such as `"password": "Password"` in translation files; the value must look like a password or a hash.
- `--reporter` on the command line removed the package reporter, so a scan could not fail; it now stops with `RUN_REPORTER_FLAG` and the flag to use.
- Responses whose body the page never read (e.g. `fetch` without `.json()`) were lost when the test ended before the body arrived; the collector now waits for them.

### Added

- Documentation: README (set-up, modes, baseline, configuration, rules table, reports, CI examples for GitHub Actions, GitLab and Azure DevOps, limits), one page per rule in `docs/rules/` and `docs/troubleshooting.md` with every code.
- HTML report (`reports/pw-sec/report.html`): one offline file with the outcome, filters (classification, severity, confidence, rule group, origin, test), grouping by rule, origin or endpoint, finding details with evidence, tests, why/fix/false positives and a ready baseline entry, the coverage of the run and the box "What this scan does not cover".
- SARIF 2.1.0 (`reports/pw-sec/results.sarif`) for GitHub code scanning and other security dashboards: every rule with help, CWE/OWASP tags and `security-severity`, findings located at the test that first saw them, stable fingerprints. JUnit XML (`reports/pw-sec/junit.xml`, `report.junitPath`) for GitLab, Azure DevOps, Jenkins and other CI: one suite per rule group, blocking findings as failures, baseline entries as skipped.
- The reporter: a start banner (mode, scope, rules, gate, baseline), findings deduplicated across the run and classified against `security-baseline.json` (new, accepted, wontfix, false-positive, expired; resolved and not covered entries), a summary of at most 30 lines, `reports/pw-sec/report.json` and `reports/pw-sec/outcome.json`, and the exit code: new findings above the gate (1), expired entries (2), tool errors (3) or no traffic in scope (4) fail the run. `PW_SEC_MODE=baseline` writes the baseline (sorted, notes and dates kept, resolved entries pruned except in filtered runs) and prints the diff.
- Rules for tokens and data (`data.*`: tokens in URLs, unsigned, endless, long-lived JWTs and JWTs with sensitive claims, passwords and hashes in responses), information disclosure (`disclosure.*`: stack traces, SQL errors, server versions, debug pages, private IP addresses, directory listings, source maps, server errors) and the browser (`browser.csp-violation`, `asset.sri-missing`, `browser.open-redirect-candidate`, `browser.reflected-param`). The catalog now has all 44 rules of the `recommended` preset (46 in `strict`).
- Rules for security headers (`header.*`: CSP missing/unsafe/incomplete/report-only, clickjacking, HSTS missing/weak, nosniff, Referrer-Policy, Content-Type; Permissions-Policy and COOP in the `strict` preset), cookies (`cookie.*`: Secure, HttpOnly, SameSite, long-lived sessions), CORS (`cors.*`) and transport (`transport.*`: cleartext, mixed content, forms over HTTP, outdated TLS). Each rule documents why it matters, how to fix it (nginx, Express, Spring) and known false positives.
- API tests are scanned too: calls of the `request` fixture, `page.request`, `context.request` and contexts registered with `trackRequestContext()` / `security.trackRequestContext()` become records of source `api`, analysed by the same rules where they apply. Wrapped methods return the original promise, value and error. Works together with `playwright-performance-regression` (use `withSecurity(withPerf(...))`).
- `withSecurityFixtures()`, `trackContext()` and the `security` fixture (`playwright-security-scan/fixture`): in scan mode the browser contexts of each test are scanned passively — responses in scope, CSP violation events, and the cookie jar and Web Storage at the end of the test — and the redacted findings are attached to the test result. Bodies are read with limits, static assets once per worker. Without `PW_SEC_MODE` only an inactive `security` fixture is added.
- First rules: `header.xcto-missing`, `data.secret-in-asset`, `data.token-in-storage`.
- `withSecurity()` and `defineSecurityConfig()` (`playwright-security-scan/config`): `PW_SEC_MODE=scan|baseline` turns the scan on, the package reporter is appended, and the package config is validated with suggestions for mistyped options and rule ids. Without `PW_SEC_MODE` the Playwright config is returned unchanged. `PW_SEC_CONFIG` points to another config file.
- Rule presets `recommended` (default), `strict` and `minimal`.
- JSON Schemas of the file formats (`schemas/`, exported as `playwright-security-scan/schemas/*`): test attachment, baseline file, run report and outcome file.
